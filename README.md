# DRIVE-MATIC

Site corporate de detail d'equipements automobiles a destination du grand public, avec un espace partenaire authentifie (~100 partenaires).

> Documentation technique de reprise. Les specifications fonctionnelles sont dans [docs/PRD.md](docs/PRD.md), les regles pour l'agent IA dans [CLAUDE.md](CLAUDE.md).

## Stack

| Couche | Technologie |
|--------|-------------|
| CMS / backend | Drupal 11 (PHP 8.3, MariaDB 10.11) |
| Templating | Twig |
| JavaScript | Vanilla JS (comportements Drupal) |
| Styles | SCSS (architecture SMACSS + nommage BEM) |

## Prerequisites

- **PHP** >= 8.3 et **Composer** 2.x
- **Node.js** >= 20 et **npm** (outillage front : ESLint, Stylelint, Prettier)
  - ⚠️ **Contrainte réelle, pas indicative** : `sass ^1.80` est **ESM-only**. Sous un Node < 20, `npm run css` s'interrompt sur `ERR_REQUIRE_ESM` — et si la sortie est redirigée, le build **paraît réussir** alors que les `.css` compilés restent périmés : on debugge alors un rendu qui ne correspond plus au SCSS. Vérifier `node -v` avant tout build front ; avec nvm : `nvm use` (voir `.nvmrc`).
- (Recommande) **Drush** pour l'administration Drupal en ligne de commande

## Installation

```bash
npm install        # outillage front (ESLint, Stylelint, Prettier)
composer install   # standards de code PHP (drupal/coder : Drupal + DrupalPractice)
```

## Verification (lint & format)

Ces commandes doivent **toutes** passer avant de considerer un travail termine (cf. `/done`) :

```bash
npm run lint          # JS (ESLint) + SCSS (Stylelint) + PHP/Twig (PHPCS)
npm run format:check  # verification du formatage (Prettier)
npm test              # placeholder — strategie de test a definir (voir docs/PRD.md)
```

Correction automatique :

```bash
npm run lint:fix      # eslint --fix, stylelint --fix, phpcbf
npm run format        # applique le formatage Prettier
```

Scripts granulaires : `lint:js`, `lint:css`, `lint:php`. Config : `eslint.config.mjs`, `.stylelintrc.json`, `.prettierrc.json`, `phpcs.xml.dist`.

## Architecture

Projet **Drupal 11** (`drupal/recommended-project`), docroot **`web/`**.

- **Thème front** : `drive_matic` (`web/themes/custom/drive_matic/`) — thème **custom autonome** généré via `starterkit` (`base theme: false`, sans `stable9`, D12-proof), **SDC-first** (composants dans `components/`).
- **Thème admin** : **Gin** (`gin.settings.classic_toolbar: horizontal`), avec la **barre du cœur** (`toolbar` + `admin_toolbar`) — barre noire « Gérer / admin » surmontant le menu horizontal. ⚠️ **Deux modules doivent rester désinstallés** ([ADR-012](.claude/decisions/012-presentation-admin-front.md)) :
  - **`gin_toolbar`** : actif, il reprend la main sur la barre **du front** et rend sa propre version claire à icônes, différente de la présentation retenue. Le paquet Composer, lui, **reste sur disque** — `drupal/gin` l'exige en dépendance ferme, il est donc impossible de le supprimer ; seule la dépendance racine redondante a été retirée de `composer.json`. Un `drush pm:enable` ou une recette qui le réactiverait changerait la barre du front sans autre signe.
  - **`navigation`** (cœur) : dès qu'il est actif, `gin_toolbar` pose `gin--core-navigation` et **sort avant** d'appliquer la classe horizontale — la barre latérale verticale du cœur gagne et le réglage de Gin devient silencieusement inopérant.
- **Onglets locaux sur le front** (Voir / Modifier / Supprimer…) : carte grise posée en `fixed` en haut à droite, qui suit le défilement. La règle vit dans `src/scss/_local-tasks.scss` (cf. ADR-012). Le crayon vient des **liens contextuels** du cœur, il n'est pas dessiné par le thème. Le décalage haut suit `--drupal-displace-offset-top`, la variable posée par `Drupal.displace`.
- **CSS hors SDC** — onze fichiers, tous des **exceptions assumées et commentées** dans `style.scss` : le markup vient du cœur ou d'un module, il n'appartient à aucun composant. `_local-tasks.scss` (onglets d'admin, ADR-012), `_forms.scss` (widgets de formulaire et carte du webform, [ADR-015](.claude/decisions/015-habillage-des-formulaires.md)), `_page-title.scss` (bloc titre de page), `_pager.scss` (pagination du cœur), `_views-faq.scss` (filtre exposé de la FAQ, rendu par Views + Better Exposed Filters, et sa zone « aucun résultat »), `_breadcrumb.scss` (fil d'Ariane, `system_breadcrumb_block` via Easy Breadcrumb, [ADR-023](.claude/decisions/023-fil-ariane-style.md)), `_user-login-form.scss` (formulaire `user_login_form`, page `/user/login`), `_user-pass-form.scss` (formulaire `user_pass`, page `/user/password`), `_personal-information-form.scss` (`FormBase` « Mes informations personnelles », espace partenaire), `_user-edit-form.scss` (formulaire `user_form`, page `/user/{uid}/edit` réduite pour un partenaire — cf. F12 ci-dessous) et `_user-logout-confirm-form.scss` (formulaire `user_logout_confirm`, page `/user/logout/confirm`, [ADR-027](.claude/decisions/027-confirmation-deconnexion.md)). Tout le reste est en SDC.
- **Formulaires de contenu** : présentation unifiée en **deux onglets horizontaux** (`field_group`), champs techniques désactivés, alias d'URL par **Pathauto** (`/[node:title]`). Convention et pièges dans [CLAUDE.md](CLAUDE.md) et `docs/content-model.md`.
- **Build front** : les **fondations** SCSS (`src/scss/` → `css/style.css`, library `drive_matic/global`) et le **CSS des SDC** (`components/**/*.scss` → `.css` co-localisé, auto-attaché par SDC) sont compilés par Dart Sass + PostCSS/autoprefixer. Scripts npm `css` (`css:foundations` + `css:components` + `css:prefix`), `build`, `css:watch`. Le `.css` généré des SDC est un **artefact** (ignoré par Prettier via `.prettierignore` — Sass impose des choix que Prettier refuse) ; seul le `.scss` source est vérifié (Stylelint + Prettier). `css:components`/`css:watch` portent un second `--load-path=src/scss` (en plus de `node_modules`) pour que les SDC puissent `@use` un partial de fondation — utilisé par `_button-mixins.scss` (ci-dessous), seul cas à ce jour.
- **Boutons partagés** ([ADR-029](.claude/decisions/029-mixin-boutons-partage.md)) : `src/scss/_button-mixins.scss` expose des mixins Sass (`dm-btn-red`/`dm-btn-grey`/`dm-btn-outline` pour les couleurs de fond + survol, `dm-btn-height` pour la hauteur ~46px) consommés via `@include` sur le sélecteur propre à chaque SDC/fondation — le CSS reste co-localisé, seules les valeurs sont centralisées. Tout nouveau bouton plein rouge/gris ou contour doit passer par ce mixin plutôt que redupliquer les couleurs.
- **Espacement et unités** ([ADR-013](.claude/decisions/013-espacement-et-unites.md)) : trois tokens portent tout le rythme — `--dm-space-element` (24px, entre éléments d'un bloc — valeur **unique**, y compris entre mobile et desktop), `--dm-space-block` (32px, `padding-block`, donc 64px entre deux blocs), `--dm-gutter` (`padding-inline`). **La gouttière est un `padding-inline`, jamais un `margin-inline: auto`** : celui-ci ne fait que centrer une largeur plafonnée et ne garantit rien sous ce plafond — c'est ce qui faisait toucher le bord au jumbo, à la grille et aux actualités en responsive sans que ça se voie à 1440. Plafond = contenu + 2 gouttières. **Unités : espacement en `px`, typographie en `rem`** (le texte suit la préférence du navigateur, la mise en page ne bouge pas). ⚠️ Deux pièges : les marges du premier/dernier enfant d'un champ **texte riche** sont neutralisées dans les fondations (`.text-formatted`) — sinon les 16px du `<p>` s'ajoutent à l'écart du bloc ; et une marge ne se pose qu'avec `:not(:last-child)`, un champ optionnel vide pouvant faire du titre le dernier élément affiché (le reset ne neutralisant que les marges du `body`, un titre seul reprendrait sinon celle du navigateur).
  - **Bascule mobile-first (addendum ADR-013 du 24/08)** : `--dm-gutter`, `--dm-space-page` et l'échelle de titres (h1/h2/h3) portent chacun une valeur mobile de base (mesurée sur les maquettes mobiles) **et** une surcharge `@media (width >= 992px)` qui restaure la valeur desktop d'origine — `--dm-gutter` vaut ainsi 16px en mobile, 40px à partir de 992px. `--dm-space-element` n'est PAS concerné (cf. ci-dessus, valeur unique).
  - Un **quatrième token** cadence le gabarit de page : **`--dm-space-page`** (13px mobile / 49px desktop, palier 992px), mesuré sur les maquettes comme l'écart entre le filet du header et le titre de page. Il porte **toute la charpente verticale, sur toutes les pages** : au-dessus du titre, au-dessus et au-dessous d'un filtre exposé, au-dessous de la liste de contenus, avant le footer. Consommateurs : `.block-page-title-block`, `page-intro`, `news-list`, `brands-grid`, `faq-list`, `.view-faq .view-filters`, `.pager`, `.field--type-webform` (contact, partenaire — `padding-block-start` seulement en `:first-child`, quand rien ne précède le formulaire), `legal-text` (pages légales, titre → body et body → footer) — tous bougent ensemble, il n'y a aucune valeur à resynchroniser à la main. Les maquettes donnent des écarts différents d'une page à l'autre (113/103 sur les actualités, 63/84 sur la FAQ) : le rythme unique l'emporte. ⚠️ Deux paddings de gabarit **ne s'additionnent pas** : une liste qui suit un filtre ne repose pas son `padding-block-start` (d'où le seul `padding-block-end` de `faq-list`).
  - Un **cinquième token** porte la largeur horizontale : **`--dm-content-column` (900px)**, la mesure commune aux maquettes, **retunable par gabarit** ([ADR-016](.claude/decisions/016-colonne-de-contenu.md)). Deux retunes à ce jour : `body.page-node-type-news { --dm-content-column: 960px }`, pour que la page de détail d'une actualité s'aligne sur son bloc `text_left_aligned` plutôt que d'y faire cohabiter deux colonnes ; et `body.page-node-type-legals { --dm-content-column: 960px }` (ADR-019). Le retune vit sur le **`<body>`** parce que le bloc titre de page est un **frère** du contenu du node (bloc du cœur en région `content`) : une valeur posée sur le SDC ne l'atteindrait pas. Consommateurs : `.block-page-title-block`, `news-article`, `video-centered`, `image-centered`. ⚠️ **Le token n'est pas universel** — `text_left_aligned` (960, la référence de ce gabarit), `page-intro` (450), `faq-list` (900), `news-list`, `brands-grid` et `legal-text` (565) gardent leur valeur littérale : aucun n'apparaît sur un gabarit retuné. Avant de retuner un nouveau gabarit, vérifier que les composants qui y figurent consomment bien le token — sinon ils ne suivront pas, **sans erreur ni signe visible**. ⚠️ **Le retune `legals` n'est actuellement consommé par rien** : la maquette CGV (469-11689) mesure son body à ~1130px, pas 960 — `legal-text` garde son plafond littéral plutôt que de consommer ce token (signalé dans `_tokens.scss`, décision d'ADR laissée ouverte).
- **`figure` n'est pas dans le reset global** : le navigateur y pose `margin: 1em 40px`. Tout SDC dont la racine est un `<figure>` (`video-centered`, `image-centered`, `news-article`) doit poser `margin-block: 0` — sinon 16px parasites s'ajoutent au-dessus et au-dessous, et l'écart entre deux blocs passe de 64 à 80 sans que rien ne le signale. `margin-inline: auto` masquait déjà les 40px latéraux, d'où une détection tardive.
- **Config** : versionnée dans **`config/sync/`** (`drush cex` / `drush cim`). Après avoir écrit de la config à la main, lancer `drush cim` puis **`drush cex`** pour la réécrire sous forme canonique (Drupal trie les clés) avant commit.
- **Breakpoints** : `drive_matic.breakpoints.yml` (xs→xxl, 1x/2x).
- **Modules clés** : Paragraphs, Webform (+ reCAPTCHA v3, Honeypot), Media (+ Media Library, Responsive Image) + Crop + Image Widget Crop, Metatag, Pathauto, Redirect, Simple Sitemap, Rabbit Hole (fragments sans page publique), Linkit + Link Target (liens internes/externes + cible), Video Embed Field, Symfony Mailer (+ Mailer Transport), Better Exposed Filters, Easy Breadcrumb, Twig Tweak, Rename Admin Paths.
- **Patchs contrib** : versionnés dans **`patches/`** et déclarés dans `extra.patches` de `composer.json` (`cweagans/composer-patches`, `composer-exit-on-patch-failure: true` — un patch qui ne s'applique plus fait échouer l'install au lieu de passer inaperçu). Un seul à ce jour : `easy_breadcrumb` 2.0.9, dont `normalizeText()` réduit les suites d'espaces avec un `preg_replace('/\s{2,}/')` **sans le modificateur `u`** — en mode 8 bits les tables PCRE classent l'octet `0xA0` parmi les blancs, donc le second octet d'un « à » était mangé et le fil d'Ariane affichait un `�`. Le titre de page, la balise `<title>` et la valeur en base étaient corrects : seul le fil d'Ariane cassait. ⚠️ **`composer reinstall <paquet>` échoue avec composer-patches v1** (double désinstallation) **après avoir supprimé le dossier du module** : remonter avec `composer install`, qui réinstalle et applique les patchs.

**Base de données locale** : MAMP MySQL (8889), base `drivematic`. `settings.php` (gitignoré) porte les accès locaux + `config_sync_directory = ../config/sync`.

**Système de fichiers privé** : `$settings['file_private_path'] = dirname(DRUPAL_ROOT) . '/private'` dans `settings.php` (gitignoré) ; le dossier `private/` est à la racine, hors docroot, gitignoré. ⚠️ **Sans ce réglage, Drupal retire silencieusement** tout élément de formulaire en `#uri_scheme: private` — ni log ni message, le champ n'existe simplement pas dans le rendu (c'est ce qui faisait disparaître la pièce jointe du SAV). **À reporter sur chaque environnement**, `settings.php` n'étant pas versionné.

**E-mails** : gérés par **Symfony Mailer** (+ `mailer_transport`). Le transport par défaut versionné est `sendmail` ; en **local**, les mails sont routés vers **Mailpit** (SMTP `127.0.0.1:1025`, UI `http://localhost:8025`, non démarré automatiquement par MAMP Pro — lancer `mailpit` séparément) via un override dans `settings.php` (gitignoré) : `$config['mailer_transport.settings']['default_transport'] = 'mailpit';`. La prod définira son propre transport SMTP. ⚠️ Le logo des e-mails webform (`logo-drive-matic-legrand-email.png`) est référencé par une **URL absolue de prod** codée en dur (cf. section E-mails webform ci-dessous) : il ne s'affichera jamais dans Mailpit tant que le thème `drive_matic` n'est pas déployé sur `www.drivematiclegrand.com` — vérifié le 2026-08-25 (l'URL répond 200 en `text/html`, pas l'image). Pas un bug, se résout au déploiement.

**Anti-spam** : le webform contact utilise **reCAPTCHA v3** (+ Honeypot + time restriction). La **clé site** est versionnée (`recaptcha_v3.settings`), la **clé secrète** n'est **jamais commitée** : elle est posée dans `settings.php` (gitignoré) via `$config['recaptcha_v3.settings']['secret_key'] = '…';`. reCAPTCHA v3 étant lié au domaine, sa validation ne se teste qu'en préprod/prod (ajouter le hostname local aux domaines de la clé Google pour tester en local).

**Images** — deux circuits distincts depuis [ADR-018](.claude/decisions/018-images-locales-par-paragraphe.md) (2026-08-19), qui affine ADR-004 :

- **Champs à ratio imposé** (les 9 paragraphes `image_text_50`, `image_full`, `history_element`, `grid_element`, `jumbo_home_element`, `product_cross_element`, `product_image_element`, `product_video_element`, `video_centered`, + `news.field_photo`, + `contact.field_photo` depuis l'addendum du 2026-08-20) : **champ image local** (pas d'entité Media), un fichier **par usage**, recadré par `image_widget_crop` **scopé au seul ratio du bundle** (`crop_1_1` / `crop_16_9` / `crop_12_5`, obligatoire à l'enregistrement — `crop_types_required` porte exactement ce ratio). Rendu par formatter `responsive_image` (style `dm_<ratio>`, WebP + fallback, 6 breakpoints). Le recadrage étant lié au **fichier**, réutiliser la même photo ailleurs avec un autre cadrage exige un **nouvel upload** (pas de sélection média) — assumé : c'est le point qui a motivé l'ADR.
- **Champs sans ratio imposé** (`image_centered`, `image_text_100`, `product_characteristics`, `brand`) : toute image reste une entité **Media** (bundle `image`) réutilisable, widget `media_library_widget`. Le rendu passe par le formatter `entity_reference_entity_view` en mode d'affichage `free` — pas de recadrage requis (`crop_types_required` est **vide** sur les deux modes de formulaire média : rien, dans le périmètre actuel, n'impose plus de ratio à l'import). `node.field_image` (storage node) ne porte plus que `brand` — `contact` en est sorti le 2026-08-20.

⚠️ Le recadrage reste **obligatoire et manuel** partout où un ratio est imposé (tranché le 2026-08-18, cf. ADR-004) : les styles `dm_<ratio>_*` enchaînent `crop_crop` (type de crop correspondant, sans `automatic_crop_provider`) puis `image_scale`. **Sans entité `crop` enregistrée**, l'effet est un **no-op silencieux** : l'image garde le ratio de sa source et le rendu n'est **pas** au ratio annoncé (un 3:2 passe pour un 16:9 approximatif — invisible à l'œil, mesurable seulement).

- Sur les champs à ratio imposé, le widget bloque l'enregistrement tant que le crop du bundle manque (`crop_types_required`) — **aucun éditeur ne peut passer outre** depuis le formulaire.
- ⚠️ **Le seul contournement reste la création programmatique** — l'API entité ne valide pas les formulaires. **Ne pas fabriquer de recadrage par script** : signaler pour un passage en back-office.
- Sur les champs sans ratio (media-library), le recadrage appartient au couple **(fichier, type de crop)** : un média recadré pour un ratio ailleurs et **réutilisé ici ressort non recadré**, sans erreur. Contrôle rapide : lire `width`/`height` sur le `<img>` du rendu.

**Un seul titre : le `title`** ([ADR-014](.claude/decisions/014-titre-unique-porte-par-le-title.md), qui remplace l'ADR-011) : le `title` du node alimente l'affichage, le fil d'Ariane, l'alias et la balise `title`. `field_title` a été **supprimé des 12 types de contenu** (storage `field.storage.node.field_title` compris) ; ⚠️ `field.storage.paragraph.field_title` est un champ homonyme distinct — titre des blocs, 21 bundles — et reste en place. Tout rendu hors page canonique (carte, teaser, ligne de Vue) lit le `title`.

**`title` + `body`, et ce que chaque type en affiche** : les deux champs existent sur tout type indexable pour le SEO (`title` → balise `title`, `body` → méta description). L'affichage, lui, est propre à chaque type. `transform` et `product` **n'affichent ni l'un ni l'autre** : la page entière vient des paragraphes, dont le contenu est libre — aucun champ du node n'y est recopié. Les autres types affichent `title` seul ou `title` + `body`, au-dessus de leurs paragraphes / Vues / webforms ; `corporate` affiche les deux, son `body` étant le chapô (libellé « Chapô », `label: hidden`, poids -1). `configurator` n'affiche que son `title`.

**Où s'affiche le `<h1>`** : sur `homepage`, `transform` et `product`, la maquette place le titre dans un bloc — le bloc titre de page y est masqué (condition `entity_bundle:node` négée) et le premier paragraphe **portant un titre** rend le `<h1>` via la prop `heading_level` des SDC `image-full` / `text-centered`. Partout ailleurs, le bloc titre rend le `title` en `<h1>` : il est en région **`content`, poids -10**, donc au-dessus du contenu (il était en `sidebar_first`, rendue après le contenu → `<h1>` en bas de page). `_drive_matic_hero_title_bundles()` et la visibilité du bloc doivent rester alignées.

**Alias** : motif Pathauto `/[node:title]` sur tous les types publics ; **exception** `news` → `/actualites/[node:title]` (la page `all_news` vivant à `/actualites`, le segment parent est un chemin valide, ce qui donne un vrai fil d'Ariane à 3 niveaux). Aucun motif sur `homepage` ni sur les fragments.

**Sitemap** : l'inclusion est **opt-in** — un bundle sans `simple_sitemap.bundle_settings.default.node.<bundle>` n'est **pas** indexé. C'est ainsi que les 3 fragments et le bac à sable en sont exclus. `homepage` n'a volontairement pas de réglage de bundle : la racine est déjà déclarée en **lien personnalisé** (`simple_sitemap.custom_links.default`, priorité 1.0), un réglage de bundle produirait un doublon.

**Front page** : le node unique servi à `/` est résolu **dynamiquement** par le module custom **`drivematic_home`** (service `FrontPageOverride`, un `ConfigFactoryOverride`) qui surcharge `system.site:page.front` vers l'unique node `homepage` publié — **sans ID de node en dur, sans alias**, portable au seed. Les surcharges n'étant jamais exportées, la valeur versionnée reste `/node` (aucune dérive de config). Invalidation via le tag `node_list:homepage`. Fil d'Ariane et titre de page **masqués sur `<front>`** (visibilité de bloc `request_path`).

⚠️ **`FrontPageOverride` ne doit injecter aucun service** : elle résout le gestionnaire d'entités **paresseusement**, dans la méthode qui s'en sert. Une `ConfigFactoryOverride` est construite par `config.factory`, qui devient une dépendance du traducteur de chaînes dès que `locale` est installé — injecter referme la boucle (`config.factory` → surcharge → `entity_type.manager` → `string_translation` → `locale.lookup` → `config.factory`) et **le conteneur refuse de se construire** : plus une seule page, plus même de bootstrap Drush. C'est la seule dérogation à l'injection de dépendances du projet, déclarée par un `phpcs:ignore` ciblé.

**Langue** : site **monolingue français** (décision #6), `language` + `locale` installés, français seule langue et langue par défaut. Traductions d'interface importées par `drush locale:update` (15 309 chaînes, 27 projets) ; les traductions de **configuration** sont versionnées dans `config/sync/language/fr/` (193 fichiers). Fil d'Ariane : Easy Breadcrumb a désormais `alternative_title_field` **vide** et retombe donc sur le label du node, c'est-à-dire le `title` (ADR-014) ; la capitalisation automatique est désactivée.

⚠️ **Migrer une base antérieure à la bascule casse toutes les URL** : les alias portent le langcode du contenu. Sur un site passé en `fr`, les alias restés en `en` ne sont plus trouvés et chaque page retombe sur `/node/N`. Il faut repasser le contenu en français (nodes, médias, paragraphes) — l'enregistrement régénère les alias — puis **forcer** ceux des nodes marqués « alias défini manuellement » (`pathauto = 0`), que rien ne régénère. Détail dans docs/PRD.md, section 7.

⚠️ **Conséquence non traitée** : la page d'accueil n'a donc **aucun `<h1>`** — son titre visible vient du SDC `text_centered`, qui rend un `<h2>`. Contredit la décision #8 du PRD (RGAA / WCAG 2.1 AA) ; à trancher avec le placement du titre, à l'intégration des maquettes.

**Vues embarquées** (`all_news`, `faq`, `brands`) : rendues par `drupal_view()` (Twig Tweak) dans le template du node hôte, et non par un display « page » — le node garde ainsi son titre éditorial, son corps de texte et ses métatags surchargeables. Contrairement à `drupal_view_result()` (cf. blocs home), `drupal_view()` **propage les cache tags** ; pagination et filtre exposé fonctionnent en pur GET. Les lignes sont enveloppées par un SDC via un template de Vue : `views-view-unformatted--faq.html.twig` → `accordion`, `views-view-unformatted--brands.html.twig` → `brands-grid`, `views-view-unformatted--all-news.html.twig` → `news-list`. Le formulaire exposé de la FAQ reste **hors** de l'accordéon. ⚠️ **Sans cette enveloppe, la Vue n'a ni colonne de contenu ni rythme vertical** : c'est ce qui rendait la liste d'actualités collée au bord gauche.

**Balises meta** ([ADR-010](.claude/decisions/010-metatags.md)) : remplissage **automatique** par les défauts Metatag + champ de **surcharge** `field_meta_tags` (widget `metatag_firehose` en barre latérale du formulaire, masqué au rendu) sur **tous** les nodes publics, `legals` compris depuis le 2026-08-20 (auparavant seul type sans body ni champ de surcharge) — **à ajouter à chaque nouveau node public**. Deux étages de défauts : le défaut global `node` reste sur `title: [node:title] | [site:name]` et **chaque bundle public a son propre défaut** `metatag.metatag_defaults.node__<bundle>` en `[node:title] | [site:name]` (ADR-014), `description: [node:summary]` comprise depuis que le bundle porte un `body`. ⚠️ Sur `<front>`, Metatag applique son défaut spécial **`front`** qui **remplace** les défauts `node`/`node__homepage` : le mapping y est donc recopié, en gardant `canonical_url: [site:url]` (la canonique de l'accueil doit rester la racine, pas `/node/<id>`). La surcharge par le champ du node s'applique malgré tout sur l'accueil. Détail et raison dans `docs/content-model.md`.

**Shell de page (SDC)** : l'ossature globale passe par deux SDC — `site-header` (header riche, livré le 2026-08-20 — F2) et `site-footer` (footer riche, livré le 2026-08-20 — F2). `templates/layout/page.html.twig` les embarque (`{% embed 'drive_matic:site-header' %}` / `site-footer`).

**Header riche** (`site-header`, [ADR-021](.claude/decisions/021-cartes-mega-menu.md) + addendum) : menu principal (4 rubriques — Auto-école, Véhicule PMR, Drive Matic, Assistance) chargé **directement** via le service de menu dans `hook_preprocess_page()` (`_drive_matic_main_navigation()`), pas par un `system_menu_block` (le bloc `drive_matic_main_menu` existe mais est désactivé — redondant) : seule cette forme permet de distinguer, par rubrique, les enfants avec visuel (rendus en carte via `field_nav_card_image`, champ sur `menu_link_content`) des enfants sans visuel (rendus en lien texte, `item.link_groups`). L'arbre est chargé sur **3 niveaux** : un enfant de niveau 2 qui a lui-même des enfants (`<nolink>`) n'est jamais rendu comme lien, seuls ses propres enfants forment une colonne de liens dédiée — nécessaire pour Drive Matic (3 colonnes séparées par des filets, dont un plus resserré que l'autre) ; les autres rubriques retombent sur un unique groupe. Desktop (flyouts inline, **pleine largeur de page** via l'échappatoire `calc(50% - 50vw)` posée sur le panneau — cf. CLAUDE.md — le contenu se recentre à 1440px dans `.site-header__panel-inner`) et mobile (tiroir `<dialog>` + sous-panneaux, même pattern que `help-modal`) rendent la même arborescence dans deux balisages distincts, bascule CSS à 992px (« lg »). Le dropdown/panneau « Espace partenaire » (5 liens, cas limite F2) reste rendu par le bloc standard (`page.secondary_menu`, menu `account`) dont la visibilité est gatée côté serveur par une condition de rôle (authentifié) — jamais par CSS/JS seuls ; il reste `right: 0` relatif à `.site-header__bar` (pas concerné par l'échappatoire plein-largeur, ce n'est pas un mega-menu). Téléphone et bouton « Demander un devis » (→ page `contact`, F10 — corrigé le 24/08, il pointait auparavant vers `configurator`/F14, une page partenaire authentifié inatteignable en anonyme) sont des données de marque fixes, codées en dur comme dans le footer. ⚠️ **Tiroir mobile (corrigé le 24/08)** : le bouton « Demander un devis » du pied de tiroir (`&__drawer-foot > &__cta`) est en pleine largeur, pas centré sur son contenu ; le sous-menu « Drive Matic » (3 groupes de liens) n'affiche plus ses filets de séparation en mobile — liste plate à écart uniforme de 24px, le filet cartes → liens des rubriques Auto-école/PMR n'étant pas concerné (repéré par sélecteur de position, `&__links + &__panel-divider`). Amélioration progressive : sous `html.no-js`, la nav desktop reste toujours visible et déployée (hamburger/tiroir n'existent que sous `html.js`) — même principe que l'accordéon. Les 7 champs `field_nav_card_image` (3 Auto-école + 4 PMR) sont recadrés (16:9, geste manuel dans le widget, jamais par script — cf. ADR-004/018).

**Footer riche** (`site-footer`, [ADR-020](.claude/decisions/020-footer-riche-menus.md)) : logo + coordonnées codés en dur (données de marque, pas du contenu éditorial) ; solutions/PMR/assistance via un menu custom **`footer-solutions`** (2 niveaux, parents en route `<nolink>` = titres de colonne non cliquables) ; liens légaux via le menu core **`footer`**, désormais peuplé. Les deux sont rendus par des blocs (`drive_matic_footer_solutions_menu` / `drive_matic_footer_legal_menu`, région `footer`) que `page.html.twig` indexe individuellement (`page.footer.<id_du_bloc>`) pour alimenter 2 slots distincts du SDC — pas la région entière comme pour le header. ⚠️ **Le cœur pose `.menu-item { padding-top: 0.2em }`** (rythme d'une liste verticale) : à neutraliser explicitement dès qu'un menu Drupal est restylé en colonnes flex, sinon son premier élément se décale de 3,2px par rapport à un titre codé en dur voisin (rencontré sur « Restons connectés »).

**Paragraphes / SDC** : chaque paragraphe = un type Paragraph + un **SDC** (`components/<nom>/`) ; la liaison se fait via `paragraph--<type>.html.twig` (`{% embed 'drive_matic:<nom>' %}` → props + slots accédés par `{{ block('nom') }}`).

**SDC hors paragraphes** : `site-header` (header riche), `site-footer` (footer riche) ; `news-card` (carte du bloc home), **`news-teaser`** (ligne de la liste `all_news` — même contenu **plus la date**), **`news-list`** (son enveloppe : colonne de contenu + rythme vertical) et **`news-article`** (les champs du node sur la page de détail : date centrée, visuel + légende, corps) ; `brand-logo` (tuile) et **`brands-grid`** (grille de la page Marques, là où la home défile) ; `video-play` (pastille inclue par les façades vidéo) ; **`help-modal`** (aide illustrée d'un champ de formulaire, cf. ADR-015). Un même SDC peut servir un paragraphe **et** une Vue : la FAQ réutilise `accordion` + `accordion-element` en rendant chaque node `question` en mode `teaser` — zéro JS ajouté, le behavior existant s'applique.

- ⚠️ **Une enveloppe de node ne doit pas porter la colonne sur sa racine** : les paragraphes portent déjà la leur, ils subiraient une **seconde** gouttière (960 → 880 sur `news-article`). D'où le sous-élément `news-article__lede`, qui groupe les seuls champs du node, les blocs restant en dehors.
- ⚠️ **`{% if block('x') is not empty %}` ne suffit pas dans un SDC** : un champ vide rend un slot fait d'**espaces**, que le test `empty` laisse passer — d'où une enveloppe vide et sa marge. Écrire **`{% if block('x')|trim is not empty %}`**. Le piège ne se voit pas partout : quand un champ n'a **aucune** valeur, le formatter ne produit pas de `content.field_*` et le slot est vraiment vide (cas de `text_left_aligned`).

- **Convention prop/slot** : les champs **scalaires** (titre, légende, options) sont passés en **props** (`paragraph.field_x.value`) et **masqués** dans le view display ; les champs **renderable** (description, lien, fichier, image, vidéo) sont injectés en **slots** via leurs formatters (`content.field_x`, donc présents dans le view display).
- **Storages de champ partagés** sur l'entité `paragraph` : `field_title` (string), `field_description` (text_long), `field_link` (link), `field_file` (file), `field_caption` (string), `field_video` (video_embed_field), `field_text_position` / `field_background` (list_string, options 50/50). **V3** ajoute : `field_links` (link, **card -1** — liens multiples de `grid_element`), `field_triptych_elements` (ERR, **card 3** — bloc plafonné), `field_text_top` / `field_text_bottom` (string — textes du triptyque). **V4** ajoute : `field_jumbo_elements` (ERR, **card 3** — bloc `jumbo_home` plafonné). **V5** ajoute : `field_arguments` (string, **card 3** — titres de `product_arguments`), `field_features_elements` (ERR, **card 5** — `product_features`, cible `product_image_element` **+** `product_video_element`), `field_cross_elements` (ERR, **card 5** — `product_cross`), `field_file_notice` / `field_file_doc` (file — notice technique + documentation de `product_characteristics`).
  Deux storages image distinctes depuis [ADR-018](.claude/decisions/018-images-locales-par-paragraphe.md) : `field_image` (ref media, **3 bundles sans ratio** — `image_centered`, `image_text_100`, `product_characteristics`) et `field_photo` (image locale, **9 bundles à ratio imposé**). Même nom de champ ≠ même storage entre bundles : voir cf. « Images » ci-dessus avant toute conversion de type.
- **Image** : media + **mode d'affichage par ratio** (`ratio_1_1` / `ratio_16_9` / `ratio_12_5` / `free`) sur les bundles sans ratio imposé ; champ local + `image_widget_crop` scopé au bundle sur les 9 autres — détail dans « Images » ci-dessus. Crop **requis** à l'import dans les deux cas où un ratio est imposé.
- **Vidéo** (`video_centered`) = **façade** : champ `video_embed_field` (allowlist providers `youtube`/`vimeo`, re-vérifiée serveur) + miniature média 16:9 ; l'iframe est rendue dans un `<template>` inerte et injectée seulement au clic (behavior `driveMaticVideoFacade` + `once`, bouton accessible clavier). Cf. [ADR-006](.claude/decisions/006-video-embed-facade.md).
- **Bibliothèque** (ADR-001) livrée par vagues (`docs/plans/paragraphs-sdc.md`) : **V0** `text_centered` ; **V1** `text_left_aligned`, `image_text_50` (options texte G/D + fond gris/blanc), `image_text_100`, `image_centered`, `image_full` (bannière 12:5), `video_centered` ; **V2** `accordion` + `accordion_element` (première paire **Bloc/Élément**) ; **V3** `grid` + `grid_element` (grille responsive 16:9 + liens multiples), `triptych` + `triptych_element` (3 blocs chiffre/accroche, **plafonné 3**), `history` + `history_element` (frise **slideshow Swiper**, image **ou** vidéo) ; **V4 (home)** `jumbo_home` + `jumbo_home_element` (bannière slideshow, plafonné 3), `news_home` / `brands_home` (blocs à **Vue** en slideshow, cf. ci-dessous) ; **V5 (produit)** `product_arguments` (1 à 3 titres), `product_features` + `product_image_element` / `product_video_element` (présentation « swipe » en **slideshow**, plafonné 5, image **ou** vidéo en façade), `product_characteristics` + `product_characteristic_element` (image **sans crop** + N caractéristiques + notice/documentation téléchargeables), `product_cross` + `product_cross_element` (cross-selling en **grille de cartes liées**, plafonné 5). **Bibliothèque ADR-001 complète (27 paragraphes).**
- **Blocs home à Vue** (`news_home`, `brands_home`, V4) : titre (prop) + lien « voir tout » (slot) + un **slideshow d'entités** rendues en **mode d'affichage `card`** (SDC `news-card` / `brand-logo` via `templates/content/node--{news,brand}--card.html.twig`). ⚠️ **Swiper exige `.swiper-wrapper` en enfant DIRECT** : on **n'embarque pas** la Vue complète (`drupal_view`, qui ajoute `.view` / `.views-element-container`) mais on rend les diapositives via **`drupal_view_result()` + `drupal_entity(node, id, 'card')`** dans le template paragraphe, le SDC fournissant `.swiper-wrapper`. Le tag de cache de liste (`node_list:news` / `node_list:brand`, perdu par `drupal_view_result`) est réattaché par **`drive_matic_preprocess_paragraph`** (`drive_matic.theme`). Les marques ne sont **pas** liées (page canonique du fragment bloquée).
- **Paires Bloc/Élément** (ADR-007) : le Bloc référence ses Éléments via le **storage partagé `field_elements`** (`entity_reference_revisions`, cardinalité illimitée) ; le type d'Élément autorisé est fixé par instance (`target_bundles`). Les types « Élément » sont **exclus du placement direct** (absents du `target_bundles` de `node.page.field_paragraphs`). Réutilisable par les Blocs non plafonnés (accordion, grid, history…). Les Blocs **plafonnés** reçoivent un **storage dédié** à la cardinalité voulue : `triptych` (`field_triptych_elements`, card 3 — V3) ; `jumbo_home` (`field_jumbo_elements`, card 3 — V4) ; `product_features` (`field_features_elements`, card 5, **deux** bundles Élément) et `product_cross` (`field_cross_elements`, card 5) — V5. `product_characteristics` (non plafonné) **réutilise** `field_elements`.
  - ⚠️ **Supprimer un node ne supprime pas ses paragraphes** : `entity_reference_revisions` ne cascade pas, les paragraphes deviennent **orphelins** en base (c'est la raison d'être du purgeur d'orphelins du module). Mesuré en supprimant 11 nodes de test : 0 paragraphe supprimé, 35 orphelins à purger — et il faut **boucler**, car purger un Bloc orphelin orpheline à son tour ses Éléments.
- **Ligne cliquable d'une carte cross-selling** : `product_cross_element` porte un **titre** et un **lien**, tous deux obligatoires, alors que la maquette n'affiche qu'une ligne. Le helper **`_drive_matic_titled_link()`** (`drive_matic.theme`) compose le lien à partir du **titre** (libellé) et de l'**objet `Url` du champ** (destination), ce qui conserve les options saisies en back-office — dont la cible d'ouverture (ADR-002). Le champ lien n'est donc pas rendu par son formatter et **son libellé n'est jamais affiché**.
- **Boutons de téléchargement** ([ADR-009](.claude/decisions/009-telechargements-nommes.md)) : le **libellé est éditorial** sur **tous** les champs fichier — c'est la **description du fichier** saisie en back-office (`description_field: true` sur les 9 instances `field_file*` des paragraphes) ; **format et poids** restent calculés. Elle est **obligatoire dès qu'un document est joint** : le cœur n'ayant pas ce réglage, `drivematic_forms` ajoute un `#process` après celui de `FileWidget` (`hook_field_widget_single_element_file_generic_form_alter`) qui la passe `#required` et la renomme « Libellé du bouton de téléchargement ». Comme le cœur ne construit cet élément qu'avec un fichier joint, un champ fichier vide reste facultatif. Deux rendus, un seul comportement :
  - **document unique** → override global `templates/field/file-link.html.twig` (+ `drive_matic_preprocess_file_link()`, qui expose `download_url`, `file_extension` et `download_label`).
  - **bloc multi-documents** (`product_characteristics`) → le formatter ne convient pas (les boutons seraient indiscernables) : le helper **`_drive_matic_document_downloads()`** parcourt les champs fichier et renvoie `label/url/format/size`, le SDC rend le bouton lui-même (prop `downloads`, plus de slots `notice`/`documentation`). Comme le fichier n'est pas rendu par son formatter, ses **cache tags sont réattachés** explicitement.
  - **liste de fichiers** (`documents`, F6, maquette `398-12119`) → même mécanisme que ci-dessus mais un **seul champ à cardinalité illimitée** par section (pas plusieurs champs nommés) : le helper sœur **`_drive_matic_field_downloads()`** boucle les deltas d'un champ (`hook_preprocess_node()`, bundle `documents`). Rendu distinct des deux précédents — **ligne de liste zébrée entièrement cliquable** (SDC `documents-list`), pas le bouton contour+icône. ⚠️ [ADR-009](.claude/decisions/009-telechargements-nommes.md) anticipait une réutilisation à l'identique du rendu `product_characteristics` ; la maquette réelle en a décidé autrement (addendum du 2026-08-19 dans l'ADR).
  - Les replis en l'absence de description (« Télécharger » / nom du fichier) subsistent comme **filet** pour le contenu créé avant la contrainte ou inséré par script — plus comme un chemin éditorial.
- **Accordéon** (`accordion`) : composant **interactif** — premier behavior JS du thème (`components/accordion/accordion.js`, `Drupal.behaviors.driveMaticAccordion` + `once`, auto-attaché par le SDC, deps `core/drupal`+`core/once` via `libraryOverrides`). Pattern **disclosure ARIA** (`<button aria-expanded>` ↔ panneau `role="region"`), **fermeture du précédent** à l'ouverture, clavier natif. **Fermé par défaut sans flash** grâce à la fondation `no-js`/`js` (cf. ci-dessous) ; **amélioration progressive** : le markup serveur ne pose ni `aria-expanded` ni `hidden`, donc sans JS tous les panneaux restent ouverts et lisibles.
- **Fondation `no-js`/`js`** : `html.html.twig` pose `class="no-js"` sur `<html>` ; la lib `drive_matic/js-detect` (chargée en `<head>`, `header: true`) bascule en `js` avant peinture. Le CSS des composants à amélioration progressive gate son état « JS actif » sous `html.js` → pas de flash. NB : Drupal core ajoute aussi sa propre classe `js` (via `misc/drupal.init.js`, chargé en **footer** — trop tard pour éviter le flash) ; d'où le doublon inoffensif `class="js js"`.
- **Slideshow** (ADR-008) : **Swiper vendorisé** (`vendor/swiper/swiper-bundle.min.{js,css}`, global `Swiper` + a11y, **self-contained**/RGPD). Libs `drive_matic/swiper` (assets) + `drive_matic/slideshow` (behavior `driveMaticSlideshow` : init Swiper **si ≥ 2** `.swiper-slide`, sinon repli liste ; `prefers-reduced-motion` → `speed: 0` ; flèches masquées tant que non initialisé ; empilement sans JS). Global `Swiper` déclaré dans `eslint.config.mjs`. Premier usage : `history` (réutilisé par V4 home + V5 produit).
  - **Options par data-attribut** sur `[data-dm-slideshow]` : `data-dm-slideshow-per-view` (nombre ou `auto`, défaut `1`) et `data-dm-slideshow-space` (px entre diapositives, défaut `24`). La **pagination** (points) s'active en plaçant un `[data-dm-slideshow-pagination]` **dans le conteneur du composant** (frère de `.swiper`, cherché via `el.parentElement`) — absent = module désactivé. Utilisés par `jumbo_home` (`auto` + `20` + pagination).
  - ⚠️ **Pièges CSS du bundle Swiper** (rencontrés sur `jumbo_home`) : `.swiper-pagination-horizontal` force `position: absolute` en spécificité (0,2,0) — répéter la classe (`&__pagination.swiper-pagination`) pour la repasser en flux ; et chaque puce reçoit `margin: 0 4px` via une règle imbriquée (0,3,0) — l'annuler par `--swiper-pagination-bullet-horizontal-gap: 0` plutôt qu'en surenchérissant.
  - ⚠️ **`.swiper` bat le BEM à égalité de spécificité** : le bundle déclare `margin-left/right: auto` et `overflow: hidden` sur `.swiper` (0,1,0), agrégé **après** le CSS des SDC. Toute reprise de ces propriétés doit **répéter la classe** — `&__viewport.swiper { … }`, replis `no-js` compris — sinon elle est écrasée sans erreur (c'est ce qui neutralisait la piste débordante de `jumbo_home` et `history`).
  - **Flèches de défilement — une seule apparence pour tous les paragraphes** : les deux assets `images/icons/slideshow-{next,prev}.svg` sont l'**export des calques « Next »** de la maquette Home (`Group 4` = suivant, `Group 5` = précédent) et portent **la plaque gris clair à 80 % et le chevron**. Chaque composant ne déclare donc plus que la taille (44px), sa **position** et l'asset — plus de plaque ni de chevron masqué à redessiner, et plus de `scaleX(-1)` pour la flèche gauche (le calque « précédent » a son propre chevron). Le jumbo, dont la maquette montrait une plaque **blanche**, suit la même flèche que les autres (consigne « même flèche partout »).
  - **Flèches hors de la piste** : `jumbo_home` les superpose au visuel (dans le `.swiper`), `history` et `news_home` les placent dans l'en-tête du bloc (`news_home` avec un titre **centré** : grille `1fr auto 1fr`, la colonne vide de gauche équilibre le titre sans élément de remplissage), `brands_home` les superpose **aux extrémités de la rangée** — donc dans un wrapper positionné **hors** du `.swiper`, qui masque son débordement.
  - **Flèche centrée sur une partie de la diapositive** (`product_features`, dont la diapositive porte un visuel 16:9 **puis** du texte) : la largeur de diapositive est déclarée en **`vw`** (`--dm-features-slide: min(900px, 70vw)`) et non en `%`, pour pouvoir la réutiliser dans `top: calc(var(--dm-features-slide) * 9 / 32)` — un `%` s'y résoudrait sur la **hauteur** du conteneur. Une seule source de vérité pour la largeur de diapo et le centrage de la flèche.
  - ⚠️ **Ordre des règles imposé par Stylelint** : `no-descending-specificity` exige que la règle `:has(… .swiper-initialized)` (spécificité élevée) soit déclarée **après** toutes les règles simples du même élément (`:focus-visible`, `.swiper-button-disabled`) — sinon le build lint échoue. Le behavior cherche flèches **et** pagination dans le conteneur du composant, donc les deux placements marchent sans JS dédié ; quand elles sont hors de la piste, l'état « démarré » se lit via `:has()` (cf. ADR-008).
- **Idiome pleine largeur (full-bleed)** : `width: 100vw` + `margin-inline: calc(50% - 50vw)` — utilisé par `image_full`, `product_characteristics` (bandeau sombre), et à droite seulement par les pistes de `jumbo_home` / `history` / `news_home` / `product_features`. ⚠️ **Corrigé le 20/08/2026** : quand ce calc est posé sur un **enfant** du conteneur centré (l'en-tête ou la piste, pas `.history`/`.jumbo-home`/… eux-mêmes), son `%` se résout contre le bloc de **contenu** du parent — plus étroit de `gutter` puisque celui-ci n'a qu'un `padding-left` (le côté droit doit rester libre pour le débordement) — d'où un débordement horizontal constant de `gutter / 2` (20px), indépendant de la largeur de fenêtre et invisible à l'œil sous macOS (scrollbars en surimpression), mesurable via `document.documentElement.scrollWidth`. Corrigé en ajoutant `+ (var(--dm-gutter) / 2)` au calc sur les 4 composants concernés (cf. [ADR-008](.claude/decisions/008-slideshow-swiper.md), addendum du 20/08). ⚠️ **Réserve non traitée, distincte de ce correctif** : `vw` compte en plus la **barre de défilement**, donc sur un OS à barres classiques (Windows) l'élément dépasse encore de sa largeur (~8-15px) et le document garde un léger défilement horizontal. Invisible sous macOS, invisible aussi en capture headless. Correctif habituel si le besoin se confirme : `overflow-x: hidden` global — non posé, car il a ses propres effets de bord (`position: sticky`). **À vérifier sur Windows en recette.**
- **Façade vidéo mutualisée** (ADR-006 maj) : lib `drive_matic/video-facade` (`js/video-facade.js`, behavior générique piloté par data-attributs `[data-dm-video-facade]`/`[data-dm-video-play]`/`template[data-dm-video-embed]`), partagée par `video_centered`, `history_element` et `product_video_element` ; l'iframe embed n'est injectée qu'au **clic** (perf + RGPD).
  - **Son à l'autoplay (corrigé le 20/08/2026)** : `video_embed_field` force `mute=1` (YouTube) / `muted=1` (Vimeo) dès que l'autoplay est actif — nécessité technique du rendu serveur statique, un navigateur bloquant sinon l'autoplay sonore hors interaction. Le clic sur la façade **est** cette interaction : `driveMaticVideoFacade` lève le mute et pose `allow="autoplay; …"` sur l'iframe à ce moment précis, sans toucher au module contrib. Respecte le cas où le serveur a déjà désactivé l'autoplay (permission `video_embed_field` « never autoplay videos ») en ne touchant à rien si `autoplay` n'est pas déjà `1`. ⚠️ Le compte **UID 1** a automatiquement toutes les permissions Drupal, dont celle-ci : ce comportement ne se vérifie pas en étant connecté en administration, mais en anonyme.
  - **Pastille de lecture** : SDC dédié **`video-play`** (markup + style), inclus par les trois façades via `{{ include('drive_matic:video-play') }}` dans leur `<button>`. La CSS d'un SDC **inclus** est bien attachée — pas de dépendance à déclarer. Le visuel est l'**export du calque maquette** `images/icons/video-play.svg` (plaque blanche 70px, rayon 8, 70 % d'opacité + glyphe acier) : les couleurs sont dans le SVG, contrairement aux icônes appliquées en `mask`. Le conteneur de la miniature doit être **positionné** (la plaque se centre en absolu).

**Formulaires publics** ([ADR-015](.claude/decisions/015-habillage-des-formulaires.md)) : l'habillage vit en fondation (`_forms.scss`, scopé à `.webform-submission-form`) et sert donc tous les webforms du site. La **mise en page est déclarée par le formulaire**, pas par le CSS : les ruptures de ligne et les largeurs passent par `#wrapper_attributes` (`dm-form-row-start`, `dm-form-span-2`, `dm-form-span-3`), que le CSS traduit en `grid-column` — aucun sélecteur ne nomme un champ. ⚠️ Les règles de **grille desktop sont en fin de fichier** : à spécificité égale, c'est leur position qui les fait gagner, les remonter remet le formulaire sur une colonne.

- **Aide illustrée** : le SDC `help-modal` remplace l'infobulle `?` de Webform par un déclencheur ⓘ et un `<dialog>` natif. Le `<dialog>` est livré dans un **`<template>`** — le composant s'insère dans le `<label>` du champ, où un `<dialog>` est interdit mais un `<template>` autorisé — puis cloné dans `<body>` par le JS. Sans JS le déclencheur reste masqué et la phrase de `#help` s'affiche. Le visuel est demandé **par nom** (`#help_attributes: { data-dm-help-visual: … }`), la correspondance nom → fichier vivant dans `_drive_matic_help_visuals()` : aucun chemin de thème en configuration. ⚠️ Le hook de thème `webform_element_help` ne déclare que `help`, `help_title` et `attributes` — **il n'y a pas de variable `element`**, d'où le passage par un attribut.

**E-mails transactionnels des webforms** ([ADR-022](.claude/decisions/022-gabarit-email-webform.md)) : les 10 handlers d'email (`webform.webform.contact.yml` ×6, `webform.webform.partner.yml` ×2, `webform.webform.account_request.yml` ×2) suivent un gabarit HTML commun stocké directement dans `handlers.*.settings.body` (`html: true`, `twig: false`) — CSS **inline** uniquement (les clients mail n'exécutent ni feuille liée ni custom properties CSS). Le logo est un **PNG** dédié (`web/themes/custom/drive_matic/images/logo-drive-matic-legrand-email.png`, exporté du SVG du thème via ImageMagick — le SVG est souvent bloqué par les clients mail), référencé par **URL absolue** (`https://www.drivematiclegrand.com/...`) : contrairement au logo du header/footer, ce chemin est **codé en dur** et ne se résout pas via `active_theme_path()` (un `<img>` d'e-mail n'a pas de contexte de thème). Convention détaillée dans [CLAUDE.md](CLAUDE.md), section « E-mails webform ».

**Page de connexion** (`/user/login`, SDC `login-panel`, [ADR-024](.claude/decisions/024-mutualisation-formulaire-simple.md) + addendum [ADR-015](.claude/decisions/015-habillage-des-formulaires.md)) : accessible en anonyme via « Espace partenaire » (header, déjà câblé vers `path('user.login')`, rien à y modifier). Le formulaire core `user_login_form` n'étant pas un webform, son habillage vit dans une fondation dédiée `_user-login-form.scss` — pas de carte propre (portée par le SDC qui l'enveloppe), pas de grille multi-colonnes. `drivematic_forms_form_alter()` y ajoute : le libellé « E-mail » (`#title` avec un `#context` distinct, sans quoi la traduction fr déjà présente pour « E-mail » sans contexte — « Courriel » — l'écraserait), le libellé du bouton « Me connecter », le déclencheur d'affichage du mot de passe (`#field_suffix`, inerte sans JS) et le lien « Mot de passe oublié » (adjacent au libellé, positionné en absolu plutôt qu'en `flex` : l'astérisque des champs obligatoires repose sur `vertical-align: super`, sans effet sur un item flex — passer le `<label>` en `flex` l'aurait fait retomber sur la ligne de base). Les 3 cartes d'action (Créer un compte / Devenir partenaire / Demander un devis) résolvent leur URL par **bundle + titre** (`_drive_matic_simple_form_node_url()`), le bundle `simple_form` étant désormais multi-instance. Fil d'Ariane et titre d'onglet alignés sur « Me connecter » par deux mécanismes distincts : réglage `easy_breadcrumb.settings.replaced_titles` pour le premier, `hook_preprocess_html()` substituant le libellé **dans** la chaîne déjà composée par Metatag pour le second (écraser toute la valeur y perdrait le nom du site, les hooks de thème s'exécutant après ceux des modules).

**Espace partenaire — « Mes informations personnelles »** (F12, module custom **`drivematic_partner`**, [ADR-026](.claude/decisions/026-profil-partenaire-mes-informations.md), maquette Figma 524:20069) : route `/user/mes-informations-personnelles`, réservée au rôle **`partenaire`** via la clé de routing core `_role` (pas de permission dédiée à créer). `PersonalInformationForm` (`FormBase`, pas d'entité) reprend les champs du webform `account_request`, préremplis depuis le compte courant ; seuls Civilité/Prénom/Nom/Fonction/Téléphone sont enregistrables, l'e-mail et tout le bloc « Votre entreprise » restent en lecture seule (`#attributes: readonly`, pas `#disabled` — accessible au clavier/lecteur d'écran). 10 nouveaux champs sur l'entité `user` (`field_civility` en `list_string`, les 9 autres en `string`), exposés aussi sur le formulaire back-office de création/édition de compte (`/admin/people/*`, form display `default`, seul mode existant sur `user`).

⚠️ **`/user/{uid}/edit` (formulaire core `user_form`, `ProfileForm`) partage ce même form display** — c'est aussi la page sur laquelle un partenaire atterrit en cliquant le lien de définition de mot de passe de l'e-mail d'activation (`pass-reset-token`). `drivematic_partner_form_user_form_alter()` y masque les 11 champs de profil + `user_picture`/`language`/`timezone`, passe l'e-mail en lecture seule et redirige vers « Mes informations personnelles » après sauvegarde — uniquement quand le compte édite **son propre** compte sans la permission `administer users` (aujourd'hui, seul `administrator` — bypass `is_admin` — l'a ; `content_editor`/« Admin » ne l'a pas). Un admin éditant le compte de quelqu'un d'autre voit tout normalement. Habillage dans `_user-edit-form.scss` (cf. ci-dessus).

⚠️ **Piège rencontré** : `EntityForm::actions()` pose `$actions['submit']['#submit'] = ['::submitForm', '::save']` **directement sur le bouton** — ce `#submit` prime sur `$form['#submit']` pour l'élément déclencheur. Ajouter un callback de redirection sur `$form['#submit']` seul est donc **silencieusement sans effet** ; il faut cibler `$form['actions']['submit']['#submit'][]`.

**Déconnexion et redirection post-connexion** ([ADR-027](.claude/decisions/027-confirmation-deconnexion.md)) : le lien « Me déconnecter » du dropdown « Espace partenaire » pointe vers `/user/logout/confirm` (formulaire core `UserLogoutConfirm`) plutôt qu'une déconnexion immédiate — mis à jour directement en base (`menu_link_content` id 48, contenu, pas config). Cette route ne montre par défaut aucun texte (même absence de bloc titre de page que `/user/login`/`/user/password`, et pas de `_title` statique en repli sur cette route précise — le `<title>` du navigateur reste donc vide, hors périmètre) : `drivematic_partner_form_user_logout_confirm_alter()` réinjecte la question du core en `<p>` visible, sans dupliquer la chaîne traduite. Habillage minimal dans `_user-logout-confirm-form.scss`, aligné sur la boîte du header comme le fil d'Ariane (ADR-023). Un partenaire authentifié via `/user/login` est par ailleurs redirigé vers « Mes informations personnelles » (`drivematic_partner_form_user_login_form_alter()`, scope au rôle `partenaire`).

**Configurateur de devis — écran 1 « Configuration »** (F14 1/3, module custom **`drivematic_configurator`**, [ADR-028](.claude/decisions/028-configurateur-formbase-vs-webform.md), maquettes Figma 493:16990/606:36813/508:13222) : route `/configurer` (`_role: partenaire`), `ConfigurationForm` (`FormBase`, pas Webform — le bloc « configuration » a un cycle de vie propre incompatible avec `#multiple`). Cascade véhicule par taxonomies (marque → modèle → motorisation, ADR-003) : la logique déjà utilisée par le webform contact (`drivematic_forms`) est généralisée pour supporter plusieurs cascades indépendantes sur une même page (`drivematic_forms_vehicle_map()`, désormais publique, et `vehicle-select.js` ciblant par attribut `data-vehicle-cascade`/`data-vehicle-role` plutôt que par `name`). Blocs de configuration répétables (pattern Drupal « Add more », clés stables jamais réattribuées, max 10 côté serveur) ; 4 équipements codés en dur en attendant le catalogue F17 ; quantité de rétrovision extérieure bornée 1-2 côté serveur (`#max` de l'élément `number`, validé automatiquement par le cœur). Tout anonyme sur une route `_role: partenaire` (pas seulement `/configurer`) est redirigé vers `/user/login?destination=...` plutôt que de recevoir un 403 brut (`PartnerAccessRedirectSubscriber`, `drivematic_partner`, event subscriber sur `KernelEvents::EXCEPTION`). Étapes Devis/Livraison (F14 2/3, 3/3) hors périmètre — détail des corrections post-livraison dans `docs/active/configurateur-etape-1/verification.md`.
